At a glance

Xiguard is Netpool's in-house platform for defending its hosting network against volumetric DDoS attacks. It watches the traffic of every single IP address across all of Netpool's MikroTik edge routers, learns what normal looks like for each one, and — the moment an address is under sustained attack — blackholes just that address on the right router, verifies the block, and alerts both Netpool's NOC and the upstream ISP. When the attack is over it lifts the block and returns the IP to service on its own.

01

The problem

A hosting network carries thousands of public IP addresses. Any one of them can be hit by a distributed denial-of-service (DDoS) attack — a flood of junk traffic from thousands of compromised machines, often measured in gigabits per second.

The attacked server is rarely the only casualty. The flood has to cross the same routers and uplinks as every other customer's traffic, so one targeted address can take everyone behind that router offline. The longer the flood runs, the wider the outage.

How it was handled before Xiguard

  • Detected late. Attacks were usually noticed only after customers reported collateral outages.
  • Blocked by hand. An engineer had to log into the right router's CLI and add a blackhole route, one IP at a time.
  • Escalated by phone. Asking the upstream ISP to scrub the attack needed a person to write an email or call their NOC.
  • No single view. Traffic across several routers could not be seen in one place, and blocks were easy to forget to remove.
Key concept · RTBH

Remotely Triggered Black Hole (RTBH) routing installs a route that silently discards all traffic destined for a single /32 address. It is the industry-standard first response to a volumetric DDoS attack. The technique itself is simple — the hard part is applying it fast, to the right address, on the right router, and removing it at the right time. That is the job Xiguard automates.

02

What Xiguard does

Xiguard turns the manual runbook into a closed, automatic loop that runs for every IP address on the network, every five seconds.

01 · Observe
Collect flow data

Every MikroTik router streams flow records (NetFlow v9) to Xiguard. Nothing is installed on the routers and no traffic is mirrored.

02 · Learn
Baseline each IP

For each address Xiguard learns a moving baseline of its normal inbound traffic, and keeps adapting as the customer grows.

03 · Detect
Confirm the attack

An address is flagged only when its traffic is far above its own baseline, big enough to matter, and sustained for 30 seconds.

04 · Mitigate
Blackhole the /32

The attacked address is blackholed on the router that serves it, and Xiguard reads the routing table back to prove the block is live.

05 · Notify
Alert both NOCs

Netpool's NOC gets a technical incident report; the upstream ISP gets a formal scrubbing request with the details it needs.

06 · Recover
Release automatically

After the block expires the address is put on probation; if it stays clean it returns to normal and a recovery notice goes out.

03

How it works — architecture

Traffic data flows in from the routers over one path; enforcement flows back over another. Between them, a five-second detection cycle decides — and hands every slow action to a dedicated worker.

  1. Export. Each MikroTik router's built-in Traffic Flow feature sends NetFlow v9 records over UDP to Xiguard. No agent runs on the router.
  2. Collect. The flow collector decodes NetFlow v9 templates and records and adds each flow's bytes and packets to per-IP counters in Redis — inbound against the destination, outbound against the source — in one-second batches.
  3. Evaluate. Every 5 s the detection cycle atomically reads and resets each IP's counters, converts them to bits and packets per second, and runs the per-IP detector.
  4. Hand off. Blackhole jobs go to a top-priority critical queue and emails to a separate email queue. Detection never waits on a router or a mail server.
  5. Enforce. The mitigation worker logs into the router over the RouterOS API (port 8728, or 8729 with TLS), installs the /32 blackhole route and verifies it.
  6. Record & display. Samples, states and alerts are stored in PostgreSQL and pushed live to the dashboard. A separate job health-checks every router each minute.

04

The detection engine

A fixed threshold is wrong for almost everyone: too tight for a busy server, too loose for a quiet one. Xiguard judges each IP only against its own history.

Learning what normal looks like

For every address, Xiguard keeps an exponentially weighted moving average (EWMA) of inbound traffic — a running baseline that weighs recent samples more than old ones, so it follows a customer's natural growth without reacting to momentary bursts.

Bnew = α·x + (1 − α)·Bold   α = 2 / (N + 1)
x = latest 5-second sample · N = 720 samples (one hour) → α ≈ 0.0028. Until an IP has N samples, a running average (α = 1/(n+1)) lets the baseline converge quickly. While an IP is blackholed its baseline is frozen, so neither the flood nor the silence after the block can distort it.

Warm-up before arming

Every newly added address starts in a SAMPLING state for 120 samples (10 minutes by default). It learns, but it can neither alert nor blackhole — so adding a new /24 never produces a burst of false alarms.

Four conditions, all required

ConditionDefaultWhy it exists
Traffic > baseline × multiplier3×The traffic must be abnormal for this particular IP.
Baseline ≥ minimum baseline floor1 MbpsNear-idle IPs have meaningless multiples — 3× of almost nothing is still nothing.
Traffic ≥ minimum spike floor10 MbpsIgnore spikes too small to threaten the network.
Held continuously for the window30 sIgnore short legitimate bursts — backups, large downloads, crawlers.

The threshold is computed from the baseline before the new sample is blended in, so a sudden flood can never drag its own threshold upward and hide itself.

Lifecycle of a monitored IP

Every address moves through a small, explicit state machine. The detector only decides; separate workers carry out each decision.

StateMeaningWhat Xiguard does
SAMPLINGNewly added, still learningUpdates the baseline; never alerts or blocks.
NORMALArmed and healthyUpdates the baseline and checks the four conditions every cycle.
ALERTAttack confirmedRecords the alert, emails both NOCs, and blackholes unless whitelisted.
BLACKHOLED/32 dropped at the routerFreezes the baseline; lifts the route once the timer (default 10 min) expires.
RECOVERINGReleased, on probationNeeds 60 s of clean traffic to return to NORMAL; a renewed attack is re-blocked at once, with no fresh 30 s wait.

00:00A 2.4 Gbps flood hits an IP whose baseline is 40 Mbps (threshold 120 Mbps).
≤ 00:05First 5-second sample above all floors — the confirmation timer starts.
≈ 00:35Held for 30 s → BLACKHOLED. Blackhole job and alert emails are dispatched in parallel.
+ secondsRoute verified on the router; Netpool's NOC and the ISP NOC receive their messages.
≈ 10:35Timer expires; the Xiguard route is removed and verified gone → RECOVERING.
≈ 11:35Clean for 60 s → NORMAL; a recovery notice goes to both NOCs.

06

Mitigation and recovery

Detection is worthless if the block never lands. Xiguard treats the router as something that can fail, and checks its own work before it reports success.

Applying a blackhole

  • Dispatch. The job is queued on the critical queue at top priority; detection for every other IP carries on in parallel.
  • Connect. Router credentials are decrypted in memory only (stored with AES-256-GCM) and a RouterOS API session is opened, optionally over TLS.
  • Install. A /32 blackhole route is added, tagged with an Xiguard comment. RouterOS 6 and 7 spell blackhole routes differently, so Xiguard tries type=blackhole, then blackhole=yes, then gateway=blackhole until the router accepts one.
  • Verify. The routing table is read back. Success is reported only if the Xiguard route is really present.
  • Retry. Up to three attempts, two seconds apart.
  • Roll back honestly. If the route still isn't there, the IP returns to ALERT and a critical “blackhole failed” alert is raised — the dashboard never shows protection that does not exist.

What lands on the router

# sent by Xiguard over the RouterOS API
/ip route add \
  dst-address=203.0.113.25/32 \
  type=blackhole \
  comment="Xiguard auto-blackhole …"

The comment carries a UTC timestamp. Example values use documentation-reserved address space (RFC 5737).

Releasing it safely

  • Automatic expiry. Every 30 s an expiry job lifts blackholes whose duration (default 10 min) has passed.
  • Only its own routes. Removal matches the Xiguard comment, so routes added by engineers are never touched — and removal is verified too.
  • Probation. A released IP must stay clean for 60 s; if the attack resumes it is re-blackholed immediately.

Notifying the right people

One attack, two audiences, two very different messages — sent automatically and in parallel.

Why two emails?

A blackhole on Netpool's own router protects everything behind it, but the flood still travels down the ISP's link to reach that router. Only the upstream provider can filter it before it fills the pipe. So Xiguard sends Netpool's NOC a technical incident report, and sends the ISP's NOC a formal, ready-to-act scrubbing request with exactly the details it needs — the step that used to require a phone call.

Abridged; example values use documentation-reserved addresses and AS numbers (RFC 5737, RFC 5398). Sender details, AS number and contact information are configured per deployment.

Built so alerts never get in the way

  • Separate worker. Emails are sent by their own worker on their own queue, so a slow mail server can never delay detection or blocking.
  • Parallel delivery. Both messages are sent at the same time over async SMTP, each through its own configurable SMTP account.
  • De-duplication. An IP will not trigger repeat alert emails within a 5-minute window, so an attack that flaps does not flood inboxes.
  • Closure. When the IP returns to NORMAL, both NOCs receive a recovery notice confirming the block is removed and traffic is back to its baseline.
  • Test sends. Each SMTP configuration can be verified from the settings page with a test email.

Engineered for attack conditions

A protection system is tested at the worst possible moment — when links are saturated and every router is under load. Xiguard is designed around that moment.

Detection never waitsRouters and mail servers are the slowest things during an attack. The detection cycle never calls either; it only queues work for others.
Three isolated queuesdefault for polling and housekeeping, critical for blackhole push and release, email for alerts — each served by its own workers.
Lossless countingA Redis Lua script reads and clears each IP's counters in one atomic step, so no flow is lost or counted twice between cycles.
Burst-ready collectorA 16 MiB UDP receive buffer and one-second batched writes absorb the surge of flow records generated by the very attack being measured.
History that scalesPer-IP samples go into daily PostgreSQL partitions; expired days are dropped in one step. 30 days of traffic, 90 days of alerts by default.
Secrets protectedRouter and SMTP passwords encrypted with AES-256-GCM (fresh nonce per value); bcrypt-hashed admin passwords; HttpOnly session cookies; panel kept on a management VLAN.
Self-healing servicesEvery service restarts automatically, health checks gate start-up, and database migrations apply themselves on boot.
One-command deploymentThe entire platform — nine services — comes up with a single docker compose up on one Linux server.

Five things that set Xiguard apart

  1. Native to MikroTik. It speaks the RouterOS API directly and absorbs the RouterOS 6 / 7 syntax differences itself — no BGP speaker, route server or extra hardware between detection and enforcement.
  2. Learns every IP individually — and refuses to guess. Mandatory warm-up plus two noise floors stop idle and small addresses from being blackholed on meaningless multiples.
  3. Verifies its own actions. Every block and release is read back from the router; a failure is surfaced as a critical alert instead of being assumed away.
  4. Closes the loop with the upstream. The ISP scrubbing request — normally a manual call — is generated and sent automatically, alongside the internal incident report.
  5. Sized for a regional hosting provider. One server, no per-bandwidth licensing, and all traffic data stays inside Netpool's own infrastructure.
